- Репозиторий: `f-gav/WreckLib`. Публичная страница: https://f-gav.github.io/WreckLib/.
- Отдельный Supabase проект: `nwlthntpkmgrhmejhfqk`. WreckTrack **не менялся**, его репозиторий и база не затронуты.

- GitHub Actions выполняет CI, публикацию Pages и smoke опубликованных HTML, JS, CSS, шрифтов, Google OAuth redirect, отрицательных проверок гостевого доступа и анонимных RPC.
- Дизайн WreckTrack: четыре цветовые схемы, Georgia/Neuzeit Antiqua/Belarus/Ebbe/Old Town, мобильная навигация «Разделы / Статья».
- Статус: **работающий технический прототип, не подтверждённый полным E2E с пользовательскими данными**.

## Завершено: этап 3A
- Безопасный перенос записей и папок `move_entry`, запрет циклов, вложения в закрытые папки и межкампанейских перемещений.
- Сортировка дерева, раскрытие/сворачивание, отдельный диалог перемещения.
- Проверка первоначальной системы ролей Мастер / Игрок+ / Игрок.
- Гостевые ссылки с ограничением только на опубликованные записи; приватные изображения через защищённую Edge Function.
- Очистка собственных неиспользуемых WebP через Storage API (без прямого SQL DELETE).

## Завершено: этап 3B — корзина
- `008_reversible_trash.sql`: `entries.deleted_at` и `deleted_by`, **мягкое удаление** без физического удаления текста, секретов и изображений.
- Удаление папки скрывает все дочерние записи по цепочке родителей; исходные `parent_id` и данные сохраняются.
- Ранее отдельно удалённые вложенные записи остаются в корзине после восстановления родительской папки.
- Из корзины нельзя восстановить карточку, если её родительская папка ещё удалена — сначала нужно восстановить родителя.
- RLS обычных пользователей, Мастера, гостевые RPC и доступ к изображениям исключают все записи с удалённым родителем или собственной меткой удаления.
- Только Мастер может использовать `trash_entry`, `restore_entry`, `list_trash`. В UI есть «В корзину», список удалённых записей и «Восстановить».
- `011_block_predeleted_entries.sql` исключает создание уже удалённых записей прямым INSERT.
- **Не реализовано:** безвозвратное удаление или автоматическая очистка корзины; ничего не удаляется физически.

## Завершено: этап 3B — участники
- `009_member_management.sql`: защищённые RPC `list_campaign_members`, `change_member_role`, `remove_campaign_member`, `revoke_campaign_invitation`.
- Мастер видит email участников и их роли, назначает Игрок/Игрок+/Мастер, отзывает доступ и отменяет ожидающие приглашения.
- Владельца кампании нельзя удалить или понизить; Мастер не может случайно отозвать собственный доступ.
- При удалении участника отменяются ожидающие приглашения на его email, чтобы он не восстановил доступ по старой ссылке.
- Текущие права не сохраняются в JWT как авторитетный источник: они проверяются по таблице `memberships` при запросе; отзыв доступа действует на следующих запросах.
- UI содержит список участников и ожидающих приглашений с явными действиями.

## Критическая находка и исправление
- При проверке обнаружена особенность PostgreSQL: сравнение `NULL <> 'master'` возвращает `NULL`, которое не входит в `IF`. Это могло пропустить проверку безопасности для аккаунтов **вне кампании** в SECURITY DEFINER RPC.
- `010_deny_null_membership.sql`: исправлено 12 функций. Проверки ролей сделаны NULL-безопасными (`IS DISTINCT FROM 'master'` / явная проверка `actor is null`).
- Транзакционный SQL-тест подтвердил, что посторонний пользователь не может менять роли, просматривать состав участников, перемещать материалы, отправлять их в корзину или публиковать гостевые ссылки.
- Проверки опубликованного сайта дополнительно подтверждают: вызовы `trash_entry`, `restore_entry`, `list_trash`, `list_campaign_members`, `change_member_role` без аутентификации возвращают HTTP 401.
- `012_trash_actor_index.sql`: индекс для FK `entries.deleted_by`.

## Выполненные тесты
- SQL rollback: права Мастера, Игрока+ и Игрока, недоступность секретов и скрытых потомков.
- SQL rollback: защита владельца, изменение ролей, отзыв членства и приглашений, отказ постороннему пользователю.
- SQL rollback: удаление папки, скрытие её потомков от участников и гостей, недоступность гостевого изображения после удаления, восстановление исходной иерархии.
- SQL rollback: защита от обхода корзины прямым UPDATE; изменение с RLS может затронуть 0 строк без ошибки — это учитывается в проверке.
- CI: Node тесты структуры, авторизации, схемы, мобильного оформления и UI этапа 3B.
- Deploy: доступность опубликованных ресурсов, OAuth handshake, отклонение неверных гостевых токенов и анонимных привилегированных RPC.

## Что пока нельзя подтвердить
- В последнем запросе к действующей базе зарегистрирована одна учётная запись (Google и email identities), но кампаний, материалов, приглашений, гостевых ссылок и файлов ещё нет.
- Проверка обмена настоящими приглашениями между двумя отдельными Google-аккаунтами, положительная загрузка/скачивание WebP и восстановление через реальный браузер пока не подтверждены инструментально.
- E2E с реальными владельцем, редактором и гостем на нескольких устройствах остаётся необходимым перед публичным выпуском.
- В Supabase Security Advisor остаются предупреждения о намеренно доступных через Data API SECURITY DEFINER RPC (подробнее: https://supabase.com/docs/guides/database/database-linter/lint-0029-authenticated-security-definer-function-executable) и о настройке leaked-password protection. Нужен итоговый аудит всех функций и настроек Auth перед релизом.
- RLS на таблице `private.campaign_shares` без политик намерен: доступ к ней запрещён через прямые роли, только защищённые функции.

## Ограничения и правила
- Не менять WreckTrack или At your service!, не объединять их базы и авторизацию с WreckLib.
- Избегать публичных service_role и Google Client Secret.
- Все SQL-миграции версии `001`–`012` находятся в `supabase/`.
- Старые файлы Cloudflare в `worker/` и `migrations/` — исторический черновик, не источник для развёртывания.


## Этап 4A — Markdown, поиск и перекрёстные ссылки
- Ветка `feature/stage4-markdown-search-links`: безопасный ограниченный Markdown-рендерер, форматирование с предпросмотром, локальный поиск исключительно по доступным RLS/гостевым записям, `[[вики-ссылки]]`, обратные ссылки.
- Исходный `entries.body` остаётся текстовым; SQL-миграции этапа 4A не требуются. Текущие RLS и приватное хранение изображений неизменны.
- Новый код тестируется до публикации на отдельной ветке; подробности в `docs/stage4-markdown.md`.
- Ручной E2E с двумя настоящими аккаунтами и реальными изображениями по-прежнему не подтверждён, так как живая база не содержит кампаний.
