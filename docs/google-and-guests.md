# WreckLib — Google OAuth и гостевой просмотр

## Что уже реализовано
- Кнопка «Войти через Google» вызывает `supabase.auth.signInWithOAuth({provider:'google'})`.
- Старый email Magic Link остаётся рабочим резервным способом входа.
- Редактирование доступно исключительно роли `master` или `editor` в конкретной кампании.
- Роли выдаются по приглашению на **точный email** аккаунта: при принятии приглашения `accept_invitation` сравнивает его с `auth.users.email`.
- Не приглашённый аккаунт и полностью анонимный гость могут просматривать только опубликованное по секретной ссылке `?share=...`; вся база не стала публичным каталогом.
- Ссылка гостя выпускается Мастером, может быть заменена или отозвана.
- Секреты Мастера и материалы, скрытые вместе с родительской папкой, не возвращаются публичными RPC.
- Изображения остаются в приватном Storage; Edge Function `shared-image` после проверки токена и видимости статьи возвращает WebP. Никаких секретных ключей во фронтенде.

## Включение Google OAuth (один раз, необходимо владельцу)
1. Откройте **Google Cloud Auth Platform**: https://console.cloud.google.com/auth/overview .
2. Настройте OAuth consent screen (Branding, Audience). Для ограниченного теста при статусе Testing добавьте Google-аккаунты тестировщиков в Test users.
3. В **Clients** создайте OAuth Client ID типа **Web application**. В Authorized JavaScript origins укажите:
   `https://f-gav.github.io`
4. В **Authorized redirect URIs** укажите URL Supabase:
   `https://nwlthntpkmgrhmejhfqk.supabase.co/auth/v1/callback`
   (не ссылку GitHub Pages).
5. В Supabase: https://supabase.com/dashboard/project/nwlthntpkmgrhmejhfqk/auth/providers → Google → Enable; добавьте **Client ID** и **Client secret** только там. Секрет не вставлять в GitHub, JS или этот чат.
6. В Supabase Auth URL Configuration убедитесь, что Site URL = `https://f-gav.github.io/WreckLib/`, а Redirect URLs содержат этот URL и шаблон `https://f-gav.github.io/WreckLib/**`.
7. Откройте https://f-gav.github.io/WreckLib/ и проверьте вход Google, создание кампании и выход.

## Пользовательский сценарий
1. Мастер входит в Google и создаёт кампанию.
2. Мастер создаёт статьи и скрытые заметки, публикует только подходящие записи.
3. Для совместного редактирования он приглашает адрес Google-аккаунта с ролью **Игрок+** или **Мастер**. Приглашённый входит тем же email, затем открывает приглашение.
4. Для чтения без входа он нажимает **Создать / обновить ссылку** и делится ссылкой. Обычные вошедшие пользователи без приглашения также могут читать по этой ссылке.
5. **Закрыть доступ по ссылке** сразу аннулирует гостевой просмотр; создание новой ссылки делает старую недействительной.

## Требования к безопасности
- Зная UUID кампании, гость **не** получает доступ — требуется 256-битный токен в ссылке.
- Токен хранится в БД только как SHA-256; RPC по токену возвращают лишь опубликованные статьи и не возвращают содержимое таблицы `entry_secrets`.
- `referrer=no-referrer` на сайте снижает риск утечки токена через HTTP Referer.
- Кто обладает ссылкой, может читать опубликованное; ссылку нельзя считать персональным приглашением.
- Edge Function принимает анонимные запросы, но проверяет токен, видимость статьи и путь перед скачиванием приватного изображения.
- RPC Security Advisor пометит намеренный доступ к двум публичным функциям SECURITY DEFINER; выполняется строгая проверка токена.
- Полные E2E-тесты Google OAuth и реальных двух аккаунтов требуют действий реальных пользователей.
